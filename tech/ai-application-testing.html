NOTE 03 / AI APPLICATION QUALITY

AI 导诊类产品应该分层测什么

模型接口返回成功，只说明一次通信完成。产品是否可用、异常是否兜底、输出是否适合展示，是不同层次的问题。

主题：AI 应用测试 · 失败兜底 · 输出评估更新：2026.09.23
范围说明

本文是面向 AI 应用质量的测试设计总结，不是对任何导诊系统医疗效果的验证报告，也不提供诊疗建议。云脑诊疗平台中的 AI 导诊是项目功能背景；下述矩阵为学习示例，不能据此推断原项目已完成这些测试。

01. 先拆成四层，不把“200”当结论

  1. 输入与业务规则：信息是否足够、字段是否有长度限制、空输入与重复提交如何处理。
  2. 模型调用链：鉴权、超时、限流、上游错误、空响应和重试是否被正确处理。
  3. 输出与呈现：结构是否符合约定、是否含不应展示的原始内容、页面能否给出清楚的失败提示。
  4. 内容质量：推荐是否符合经过确认的业务准则，以及评价者之间是否能达成一致。

前三层可以大量使用确定性断言；最后一层往往不能简单等同于字符串完全匹配，需要领域人员定义评判规则、样本和复核流程。NIST 的 AI 风险管理资料强调在具体使用情境下进行测试、评估、验证与确认，而不是只依赖一次演示结果。

02. 把异常变成可执行的检查点

输入或故障可观察预期检查位置
描述为空或明显不足按产品规则提示补充信息；不直接展示编造出的确定性推荐前端提示、是否发起模型请求
模型接口超时/限流服务端按约定返回可识别错误；前端有兜底文案，不无限加载模拟上游响应、接口状态、页面
返回 JSON 缺字段/类型错误解析失败有明确处理；不把异常对象或原始文本直接渲染为正式建议解析器测试、页面渲染
输出包含 HTML/脚本片段作为不可信文本处理，不能执行脚本或拼成危险页面渲染组件、安全检查
输入夹带“忽略规则”等指令不因用户输入改变应用权限、泄露敏感配置或执行越权操作服务端权限边界、日志与输出
同一输入多次输出不同内容评估使用预先定义的容忍范围与人工复核，不以逐字相同作为唯一通过条件样本集、评审记录

OWASP 将提示注入、敏感信息泄露和不当输出处理列为大模型应用风险。这里的安全断言应放在应用边界：鉴权、输出验证与页面安全不能只靠给模型写一句“请勿这样做”。

03. 用受控替身测失败路径

把上游模型调用封装成独立接口，再在测试环境用可控替身返回固定内容，比反复调用真实模型更适合验证错误处理。至少准备四种响应：正常结构、超时、非预期状态码、字段类型错误。对每一种响应，核对后端是否记录关联 ID、前端是否结束加载状态、用户是否看到清晰且不泄露内部细节的提示。

示意的结果结构可以是：

{
  "status": "needs_more_information",
  "message": "请补充症状持续时间",
  "suggestions": []
}

它只是测试契约示意，不是原项目真实接口，也不是医学判断。真实字段、状态和提示文案应由产品、开发及相关领域人员确认。测试中不要把真实患者资料放进公开仓库、截图或第三方模型调用记录。

04. 内容质量需要样本和评价规则

如果要评估推荐内容，先整理经授权且去标识化的样本，覆盖信息充足、信息缺失、含糊表述和高风险表述等类别。为每个样本写清“什么算合格”：例如是否要求补充信息、是否超出允许的建议范围、是否有不当确定性表达。之后再由具备相应领域知识的人复核争议样本。

记录模型版本、提示词版本、参数、时间和样本集版本，才能解释一次评估结果为何变化。所谓“准确率”必须说明分母、标注规则及人工一致性；没有这些条件，不应在简历或博客写出百分比。

05. 一个可追溯的问题记录长什么样

比“AI 回答错了”更有用的记录是：输入类别、测试环境与版本、模型调用是否成功、返回结构、页面展示、期望依据、实际结果、复现概率和脱敏截图/日志位置。对偶发内容问题，可以保存多次采样结果并标明差异；对确定性解析错误，则尽量保留最小复现输入。

测试者最后要知道自己证明了什么：接口稳定不等于内容正确；安全边界挡住一类输入，也不意味着任何提示注入都不可能成功。把结论的适用范围写明，比一句“AI 功能测试通过”更有价值。
