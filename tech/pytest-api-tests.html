NOTE 02 / API AUTOMATION

用 pytest 搭一组可复现的接口测试

自动化的第一目标不是“代码多”，而是同一个用例重复运行仍能说明同一个问题：有独立数据、明确超时和可解释的断言。

主题：Python · pytest · requests · CI更新：2026.09.23
示例边界

本文配套的是独立教学服务，代码在 GitHub 示例目录。它不连接云脑诊疗平台，也不声称覆盖真实挂号系统。写作时在本地运行 python -m pytest -q，结果为 8 个测试通过；后续修改代码仍应重新执行。

01. 最小可运行环境

示例使用 Python 标准库启动一个本地内存服务，用 requests 发 HTTP 请求，用 pytest 组织测试。运行所需的依赖与命令都在仓库里，不依赖线上账号或数据库。

cd examples/appointment-api
python -m venv .venv
# 激活虚拟环境后：
python -m pip install -r requirements.txt
python -m pytest -q

每条测试用例通过 fixture 启动一台监听随机端口的服务，测试结束就关闭。这样前一个用例创建的预约不会污染下一个用例，也不会争用固定端口。真实项目里可用独立测试库、事务回滚或可控的数据清理实现同样的隔离目标。

02. fixture 让“前置状态”可重复

@pytest.fixture
def base_url():
    server = AppointmentServer(("127.0.0.1", 0))
    thread = Thread(target=server.serve_forever, daemon=True)
    thread.start()
    try:
        yield f"http://127.0.0.1:{server.server_port}"
    finally:
        server.shutdown()
        server.server_close()
        thread.join(timeout=2)

yield 前创建前置状态，之后释放资源。随机端口 0 由系统分配，减少本机端口冲突。示例的状态只在内存中，便于理解；真实服务还要考虑数据库清理、异步任务和外部依赖的稳定性。

03. 参数化覆盖同一类规则

三个必填字段有相同的预期：缺失时返回参数错误，且号源余量不变。用参数化能减少重复代码，同时在失败报告里指出具体是哪个字段失效。注意不要把可变字典作为多个参数用例的共享数据再原地修改；pytest 文档说明参数值会原样传递，并不会自动复制。

@pytest.mark.parametrize("field", ["patientId", "slotId", "requestId"])
def test_missing_required_field_does_not_take_slot(base_url, field):
    invalid = payload()  # 每次新建字典
    del invalid[field]
    response = post(base_url, invalid)
    assert response.status_code == 400
    assert response.json()["error"] == "missing_or_invalid_field"
    slot = requests.get(f"{base_url}/slots/slot-01", timeout=2)
    assert slot.json()["remaining"] == 1

04. 断言业务结果，而不是只断言 2xx

成功预约时，测试先检查创建响应，再用预约编号重新查询资源，最后检查号源余量。这样可以发现“接口声称成功，但数据没有正确更新”的情况。重复请求则检查两次返回的是同一个预约编号；并发请求争夺最后一个号源时，应恰好有一个成功、一个被拒绝。

first = post(base_url, payload())
second = post(base_url, payload())
assert first.status_code == 201
assert second.status_code == 200
assert second.json()["appointmentId"] == first.json()["appointmentId"]

这里的去重键与返回码是示例服务自己定义的契约，不是所有接口的通用标准。接入真实接口时，需要先与开发确认去重范围、有效期、请求体变化后的行为以及并发约束。

05. 超时与失败信息是测试稳定性的基础

requests 默认不会替你设置适合项目的超时。示例统一传入 timeout=2，避免服务没有响应时测试无限等待。这个值适合本地轻量示例，不应直接照搬到网络环境；接口服务级别协议、CI 环境和慢操作需要分别评估。官方文档也说明 timeout 并非整个响应下载过程的总耗时上限。

失败报告应能定位到请求、预期和实际结果，而不是只出现“assert False”。测试代码可以附加业务标识与响应文本，但敏感字段要脱敏，不要把患者资料或令牌打印到 CI 日志。

06. 接入持续集成，但不误读绿色勾号

仓库里的示例 CI 在相关代码路径发生提交或拉取请求时安装依赖并运行测试。若运行通过，它证明的是这个独立示例在该运行环境下通过，不证明真实医疗业务、前端体验或 AI 推荐质量。CI 与本地使用同一条 python -m pytest -q 命令，便于复现失败。

下一步若扩展到真实项目，应按速度分层：提交时跑稳定的单元/接口检查，部署到测试环境后再跑端到端流程；不要把需要人工判断的 AI 内容质量硬塞进“所有断言都是确定的”测试里。
