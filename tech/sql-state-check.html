NOTE 05 / DATA VERIFICATION

接口成功后，数据库该怎么核对

返回一个预约编号，只能证明接口声称成功。要判断业务状态是否一致，需要把预约记录和号源余量放到同一条规则里检查。

主题：SQL · 数据状态 · 业务不变量更新：2026.09.23
示例边界

本文的表结构和等式是独立教学示例，不是云脑诊疗平台的真实数据库设计。配套 SQLite 示例代码只在内存中运行，已本地验证 2 个检查通过。真实系统应先确认状态口径与数据权限。

01. 先写出业务不变量

假设一个简化的号源只有三种相关数据：总量 capacity、剩余量 remaining、状态为 reserved 的预约数。则可以暂定：

capacity = remaining + reserved_count

这条等式不是医疗系统的通用真理。如果业务中“待支付”也占库存、取消后不立即释放、存在超时锁定或跨系统同步，那么公式必须重写。测试人员应该先和需求、开发确认“哪些记录算占用”，再查库；否则 SQL 写得再漂亮，结论也可能错。

02. 用聚合查询找出不一致行

SELECT
    slots.id,
    slots.capacity,
    slots.remaining,
    COUNT(appointments.id) AS reserved_count
FROM slots
LEFT JOIN appointments
    ON appointments.slot_id = slots.id
    AND appointments.status = 'reserved'
GROUP BY slots.id, slots.capacity, slots.remaining
HAVING slots.remaining + COUNT(appointments.id) != slots.capacity
    OR slots.remaining < 0;

这里用 LEFT JOIN，是为了让“尚无预约的号源”也被检查；把 status = 'reserved' 放在 ON 中，则取消记录不会被算作占用。COUNT(appointments.id) 只计算非空的预约 ID，所以没有匹配预约时得到 0。最后 HAVING 留下违反规则的号源。

示例数据里，一个总量为 2 的号源有 1 条有效预约、1 条取消预约，剩余 1 时无异常行；把剩余误写为 2，就会返回异常行 (slot-01, 2, 2, 1)。单纯看“预约表里有记录”发现不了这一类问题。

03. 把 SQL 放进可复现的用例

一条完整的接口用例可以按以下顺序执行：准备独立号源与用户 → 记录初始余量和预约数 → 发送请求 → 保存响应中的预约编号 → 查询该编号及相关号源 → 执行一致性查询 → 对照预期断言。失败请求还要确认没有留下半更新：例如预约没创建却减了号源，或接口报错但数据库已有有效预约。

多用例共用一张表时，不要依赖“刚好没有其他人使用这个号源”。使用独立测试数据、随机业务标识或受控清理，才能避免彼此污染。并发场景要在请求完成后按业务允许的最终状态核对，不要把两个不同时间点的查询硬拼成一次快照。

04. 知道查库能证明什么、不能证明什么

  • 能证明：在所查询的环境、时间点和规则口径下，所选数据是否满足约束。
  • 不能单独证明：用户页面展示正确、跨服务异步处理完成、并发控制始终正确，或系统不存在其他异常。
  • 要留意：读写分离和异步同步会带来时间差；在合适的事务或等待条件下核对，并记录查询时间与环境。

真实项目中尤其要使用授权的测试库与脱敏数据。不要为了“验证”直接修改生产表，也不要把患者姓名、身份信息或数据库凭据写入公开脚本与问题截图。

05. 运行独立示例

cd examples/sql-state-check
python check.py

示例只使用 Python 标准库的 sqlite3 和 unittest，分别验证“一致状态没有异常行”和“错误余量被查出”。如果将来迁移到 MySQL，应核对实际表结构、隔离级别、状态定义与 SQL 方言，不应直接复用这个演示查询。
