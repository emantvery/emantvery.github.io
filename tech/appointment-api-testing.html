NOTE 01 / TEST DESIGN

挂号接口：从业务状态到测试用例

接口测试不能只问“返回码是不是 200”。预约成功意味着号源、预约记录和用户可见状态一起发生了正确变化。

主题：业务规则 · 状态流转 · 接口验证更新：2026.09.23
范围说明

下面的 POST /api/appointments 和字段是为了说明测试方法而设计的示例契约，不代表云脑诊疗平台的实际接口路径、字段或已完成的测试结果。真正测试前，应先以需求文档、接口文档和代码为准。

01. 先固定可观察的契约

假设预约请求包含 patientId、slotId 和 requestId。成功时服务创建一条预约、占用一个号源，并返回预约编号。这里的 requestId 是示例中的业务去重键：它只有在服务端明确实现并约定语义时，才能用来断言“相同请求只创建一次”。

POST /api/appointments
Content-Type: application/json

{
  "patientId": "patient-01",
  "slotId": "slot-09",
  "requestId": "req-20260923-001"
}

动手写用例前，至少要明确四件事：哪些角色能预约；号源何时视为可用；重复请求返回原结果还是报冲突；取消后号源能否恢复。没有这些约定，测试里的“预期结果”只是猜测。

02. 用状态而不是页面按钮组织场景

一个简化的状态链路可以写成：号源可用 → 预约待支付 → 已支付/已取消。如果业务没有支付环节，就去掉相应节点；如果存在超时释放，就增加“超时取消”。测试重点是允许的转换能完成，不允许的转换被拒绝，失败时不留下半更新的数据。

场景输入与前置条件重点核对
正常预约已登录、号源可用、字段合法创建一条预约；可用号源减一；返回的编号可查询
缺失必填项缺少 slotId 或身份信息按契约返回参数错误；不创建预约、不占号源
号源耗尽对应时段余量为零明确拒绝；记录数和余量不变
重复提交同一 requestId 连续或并发提交按约定返回相同结果或冲突；绝不能超卖或生成多条有效预约
越权请求用户尝试替他人预约，且业务不允许身份校验阻断；避免只依赖前端隐藏按钮
失效号源时段已过期或已下架拒绝预约；页面提示和服务端结果一致

边界值不要机械地写“空、最大、最小”三个词。要查真实限制：日期是否允许当天、预约数量上限是多少、患者标识的格式如何定义。边界应从规则推出来。

03. 重复请求不能只看 HTTP 方法

HTTP 规范将 POST 定义为非幂等方法；“预约接口重复发送也只创建一次”不是协议自动保证的，而是应用必须自行定义并实现的规则。测试时要区分客户端重试、用户重复点击和并发抢同一个号源。前两者可能用业务去重键处理，后一种还要验证并发控制与数据约束。

最容易漏掉的是“第一次请求已在服务端成功，但客户端超时没收到响应”。此时重试不应凭空再占一个号源。测试设计应记录两次请求的 requestId、响应、预约表和号源余量；预期结果必须与产品和后端约定一致。

04. 一条用例至少有三层证据

  1. 接口层：状态码、响应结构、业务错误码和预约编号；错误时不应返回误导性的“成功”。
  2. 数据层：预约记录数、患者与号源关联、号源余量、订单状态。需要在隔离的测试环境中查询，不能依赖生产数据。
  3. 用户层与日志：页面是否给出可理解的提示；日志是否足以串起请求，但不应泄露患者敏感信息。

如果测试失败，记录可复现的前置数据、请求、响应、时间与关联 ID，再区分“看到的事实”和“猜测的原因”。复测时使用同一套输入和预期，同时检查相关状态是否被修复。
